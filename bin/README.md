# Bootstrap pipeline

PASTA's wrapper API is regenerated from Clang headers in two stages. This document is the runbook.

## TL;DR

From a configured build directory:

```sh
ninja && ./bootstrap-macros && ninja && ./bootstrap-types && ninja
```

You need a build configured with both bootstrap flags enabled:

```sh
cmake -GNinja \
  -DPASTA_BOOTSTRAP_MACROS=ON \
  -DPASTA_BOOTSTRAP_TYPES=ON \
  -DCMAKE_BUILD_TYPE=Debug \
  ../pasta
```

Note: enabling either bootstrap flag disables installs (see `cmake/options.cmake:20`). Bootstrap builds are developer-only.

## Stages

### Stage 1 — `bootstrap-macros`

**Source:** `bin/BootstrapMacros/`
**Inputs:** Clang headers from the vendored LLVM in `vendor/llvm-project/`.
**Output:** `bin/BootstrapTypes/Generated.h` — a ~1.5 MB X-macro inventory of every Clang AST class and method PASTA wraps.
**Approximate runtime:** seconds (it's a single Clang AST traversal).

The X-macros emitted are consumed by stage 2 and by `Globals.cpp`. Format:

- `PASTA_BEGIN_CLANG_WRAPPER(name, id)` — one per AST class.
- `PASTA_PUBLIC_BASE_CLASS(name, id, base_name, base_id)` — one per public-base relation.
- `PASTA_INSTANCE_METHOD_N(cls, id, meth_id, meth, rt, ...)` — one per wrapped method (N = arity, 0–6).

Stage 1 must run after a `ninja` so that `bootstrap-macros` is built and the vendored Clang is available.

### Stage 2 — `bootstrap-types`

**Source:** `bin/BootstrapTypes/`
**Inputs:** `Generated.h` (from stage 1) + hand-curated metadata in `Globals.cpp`.
**Outputs:**
- `include/pasta/AST/{Forward,Decl,Stmt,Type,Attr}.h`
- `lib/AST/{Decl,Stmt,Type,Attr}.cpp`
- `bindings/python/src/AST/{Enums.cpp,AST.cpp,CMakeLists.txt}` and per-class binding files.

**Approximate runtime:** seconds.

The intermediate `ninja` between stages 1 and 2 is required because stage 2 (`bootstrap-types`) compiles against `Generated.h`. The final `ninja` rebuilds the rest of PASTA against the freshly-emitted wrapper code.

## When to re-bootstrap

- After bumping the LLVM submodule (any change to `vendor/llvm-project/src`).
- After editing `bin/BootstrapTypes/Globals.cpp` (rename rules, nullable annotations, blacklists).
- After editing any generator source under `bin/BootstrapTypes/Generate*.cpp`.
- After editing `bin/BootstrapMacros/MacroGenerator.cpp`.

## Validating a bootstrap run

The bootstrap is **deterministic**: re-running on a clean tree should produce zero diff against the checked-in generated files.

```sh
git status include/pasta/AST/ lib/AST/ bindings/python/src/AST/ bin/BootstrapTypes/Generated.h
```

Should be empty after a successful no-op re-bootstrap. If it isn't, either:
1. You meant to introduce a change (commit the generated diff alongside the metadata change that caused it).
2. A refactor accidentally changed codegen output (investigate; bootstrap determinism is a load-bearing invariant).

Then run the test suite:

```sh
ctest --output-on-failure
```

## Common failure modes

### "no member named X in clang::Foo"

Stage 2 generated a wrapper that calls a Clang method that doesn't exist in the current LLVM version. Causes:
- Clang renamed the method upstream → add an entry to `kCxxMethodRenames` in `Globals.cpp`.
- Clang removed the method → remove the wrapper trigger from metadata or extend `Generated.h` exclusions.

### "use of undeclared identifier `getFoo`"

Hand-written code in `lib/Compile/`, `lib/AST/Printer/`, or `lib/AST/Bounds.cpp` references a Clang symbol that moved or disappeared. Not a generator issue — fix the call site against the new Clang API.

### Bootstrap binary crashes on a class name

Likely missing categorization for a new Clang class. See the suffix-match block in `bin/BootstrapTypes/Main.cpp:102-121` and the special-case list. Add the class explicitly until the categorization refactor lands.

### New attribute spelling not handled

Clang added an attribute kind that isn't in the existing enumeration. Re-running stage 1 should regenerate `Generated.h` to include it; if stage 2 still fails, the new attribute may need a manual override in `lib/AST/AttrManual.cpp`.

### ABI breakage in `lib/AST/*Manual.cpp`

Manual override files reference Clang internals directly. When Clang changes, fix the override against the new API. These files are hand-written and authoritative — they're not regenerated by bootstrap.

## File layout

```
bin/
├── BootstrapMacros/        # Stage 1: Clang AST traversal → Generated.h
├── BootstrapTypes/         # Stage 2: Generated.h + metadata → wrapper API
│   ├── Main.cpp            # Orchestrator
│   ├── Globals.cpp         # Hand-curated metadata (renames, nullable, IDs)
│   ├── Generated.h         # Stage 1 output (checked in)
│   ├── Generate{Decl,Stmt,Type,Attr}{H,Cpp}.cpp  # Per-category emitters
│   └── ...
└── BootstrapBuiltins/      # Generates builtin function metadata (separate axis)
```
